** Surprises and decisions
Three findings drove the design and are worth not rediscovering.

=TEFUNC= is not a pure function of =(t, y)=: it advances the disturbance walks,
draws measurement noise, ticks the sampled analyzers, and latches valve sticking
on every call. Harmless under fixed-step Euler, silently wrong under any
multi-stage integrator. Hence the pure/impure split in the plan.

The RNG is bit-reproducible. =G = DMOD(G*9228907, 4294967296)= overflows 2^53, so
rounding is part of the algorithm, but IEEE fixes both the multiply and the
=fmod=. The existing Python port's noise divergence is therefore a *call-ordering*
defect, not an arithmetic one, which is why Tier 3 (RNG call-trace diff) exists
and is cheap.

Exact long-horizon trajectory matching against gfortran is impossible because
=exp= and =pow= differ by ULPs and the closed loop amplifies that. Tier 4 is
diagnostic only. The real gates are Tier 5 (equivalence testing on means *and
variances*, since the Python port's failure mode was variance collapse: reactor
pressure sigma 8.10 against Fortran's 61.48) and Tier 6 (cross-source detector
performance).

Four scoping decisions recorded in =BACKLOG.org= under Decisions.

** Surprises and decisions
*The original draws no random numbers at t=0.* Three guards line up to make it
so, and assuming otherwise is easy: I wrote a test asserting the generator
advances on the first call and it failed. =TEINIT= sets =TNEXT(I)=0.1= at
=teprob.f:1362=, so both walk loops at =teprob.f:359= and =teprob.f:372= are
skipped; the noise loop at =teprob.f:711= is gated on =TIME.GT.0.0=; and the
analyser blocks do not fire until t=0.1 and t=0.25. The measurement noise
sequence therefore begins on the *second* step. A port that starts drawing at
t=0 would diverge from the very first sample and look like an arithmetic problem.

*The first step past zero draws exactly 264 uniforms*, being the 22 continuous
measurements times the 12 uniforms =TESUB6= sums per measurement
(=teprob.f:1539-1546=). Predicted from reading the source, then confirmed by
walking the LCG forward from the seed to the observed word. This is a precise,
cheap Tier 3 checkpoint available before any model code exists.

*The oracle needs =unsafe=*, which =CLAUDE.md= previously allowed only in the
PyO3 and wasm glue. The rule now names three FFI crates and requires
=deny(unsafe_op_in_unsafe_fn)=, a safe wrapper, and a real =// SAFETY:= argument
on every block.

Smaller: rustdoc with =-D warnings= fails on intra-doc links to =Oracle= from the
crate-level docs, because the workspace doc build runs with default features and
the type does not exist there. Those two references are plain code spans now,

** Surprises and decisions
*182 of the constant assignments in =TEINIT= are single-precision literals.*
Fixed-form Fortran treats a literal with no =D= suffix as =REAL=, so assigning
it to a =DOUBLE PRECISION= variable widens a value already rounded to 24 bits.
=XMW(2)=25.4= at =teprob.f:942= stores 25.399999618530273, not the nearest
double to 25.4. =CPPRMX=1.3= stores 1.2999999523162842. 166 assignments do carry
the suffix and are full precision, so it is genuinely per-constant.

The relative error is about 1.5e-8 against a Tier 1 tolerance of 1e-13: five
orders of magnitude. A port writing =25.4_f64= would fail in a way that looks
like a deep numerical problem and is actually clerical. Found because three
layout tests failed on values I had assumed were exact, so the tests earned
their keep before any model code exists. B-0006 now requires per-literal
transcription plus a test that enumerates =D=-suffix status from the source
rather than trusting the eye.

Downstream of the same cause: the feed compositions at =teprob.f:1134-1159= are
=0.9999= and =0.0001= without suffixes, so they sum to 1 only to about 1.7e-8.
The composition test uses 1e-7, and that is not slack: a tighter bound would
assert something the original does not do.

*The uniqueness assertion in the instrumentation paid for itself immediately.*
The obvious anchor for initialising =ISD= in =TEINIT= is =TNEXT(I)=0.1D0=, which
also appears in =TEFUNC='s t=0 reset block. Matching twice would have edited both
sites. Anchoring on the =DO 550= terminator instead is unique.

*A badly chosen teeth check.* My first attempt perturbed =TIME=, and the test
still passed. Not a broken test: with no disturbances active, =TESUB8= returns
zero regardless of time and the analysers do not fire until t=0.1, so =TEFUNC=
genuinely has no time dependence at small t. Worth knowing before Tier 2 picks
sampling points, since varying time alone explores nothing.

*TESUB1 with ITY=2 is ill-conditioned, and this is the headline for B-0009.*

thousand. Suspect it first when Tier 1 moves.

*Dirichlet is sampled by spacings, with concentration fixed at 1.* Sorted
uniforms, gaps taken. No rejection, so the words consumed per sample are
fixed; no transcendental function, so no cross-platform ULP risk; fractions
non-negative by construction. A general Dirichlet(alpha) would need a gamma
sampler and give up all three. The near-degenerate compositions a small alpha
would reach are covered instead by the third pool, which draws a random
support of 1 to 8 species and is uniform on that face, so vertices and edges
are hit exactly rather than approached.

** Surprises and decisions
*The bug worth finding here changes no value at all.* =IDVWLK= multiplies the
two *endpoint* draws at =teprob.f:1529-1530= but not the *duration* draw at
=1528=. So an inactive channel still consumes all three.

The obvious optimisation is to skip the two endpoint draws when the flag is
zero, since they are multiplied by zero anyway. Doing that produces *identical
segment values*, because an inactive channel lands on =SZERO= with zero slope
either way, and leaves the generator two steps behind. Every subsequent draw in
the run then differs: the noise, the other channels, everything.

It was implemented deliberately to check the test has teeth, and the Tier 1
test caught it, on the *stream position* rather than on any value. A test that
compared only outputs would have passed. That is the entire argument for Tier 3
demonstrated at Tier 1, and it is why the ending generator word is compared on
every case rather than just the draw count: a port can make the right number of
draws in the wrong order.

*A claim of mine was wrong and the measurement corrected it.* The module first
said =TESUB6='s twelve-term sum was order-sensitive, like every balance in
=crate::balances=. It is not. Over 500,000 consecutive samples from the real
stream, summing the twelve draws forwards and backwards gives *bit-identical*
results every time.

The reason is conditioning: all twelve addends lie in [0, 1) and the running
total never exceeds 12, so every addition is between operands within a factor of
about twelve and nothing is lost to shift out. The loop is still written in call
order, because that is what the listing says, but the module now distinguishes
what is load-bearing (the draw order) from what is not (the arithmetic). A test
asserts the conditioning premise directly, so a change to =unit()='s range fails
there rather than somewhere subtler.

*Half the sweep was vacuous on the first run.* =oracle.wlk()= reads
=COMMON/WLK/=, which is all zeros until =TEINIT= runs, so the "real channel"
half of the sweep had zero spans, =H= = 0, and non-finite cubic coefficients on
both sides: 10,000 cases agreeing perfectly and proving nothing. The comparison
harness reported it as =non-finite: 10000 seen, 0 mismatched=, which is exactly
the line that made it visible. Both sweeps now call =oracle.init()= first and
assert the spans are populated.
